=> Use os conceitos de Clean Code e SOLID: São os pilares da engenharia de software para criar sistemas que não apenas funcionam, mas que conseguem evoluir ao longo do tempo sem se tornarem um pesadelo de manutenção. Enquanto o Clean Code foca na estética, clareza e legibilidade do código no dia a dia, o SOLID fornece as regras de arquitetura e design estrutural para orientar como as peças do seu software se conectam.

A) Clean Code: A Arte da Legibilidade
=> O conceito de Clean Code (Código Limpo), popularizado por Robert C. Martin ("Uncle Bob"), defende que o código deve ser escrito para seres humanos lerem, e não apenas para máquinas executarem. Um código limpo é direto, parece que foi escrito por alguém que se importa e não esconde a intenção do desenvolvedor.

A.1) Nomes Revelam Intenção
Esqueça nomes genéricos como x, data, val ou aux. O nome de uma variável, função ou classe deve dizer exatamente o que ela é ou faz.
• ❌ Ruim: int d; // dias passados
• Bom: int diasDesdeAUltimaModificacao;

A.2) Funções Devem Fazer Apenas Uma Coisa (E Fazer Bem)
Funções devem ser pequenas. Se uma função valida um formulário, salva no banco e envia um e-mail, ela está fazendo coisas demais. Divida-a em três funções limpas. Além disso, idealmente, uma função não deve ter mais do que dois argumentos.

A.3) Evite Comentários Desnecessários
O código deve ser tão claro a ponto de se autoexplicar. Comentários devem ser usados apenas para explicar por que algo foi feito de forma incomum (decisões de negócio complexas), e nunca para explicar o que o código faz. Se você precisa comentar o código para explicá-lo, reescreva o código.

A.4) Tratamento de Erros é uma Coisa Só
O tratamento de erros (blocos try/catch) deve ser isolado. Uma função que trata erros deve fazer apenas isso. O código principal fica na chamada dentro do bloco try, mantendo o fluxo limpo.

B) SOLID: Os 5 Princípios do Design Estrutural:

=> O SOLID resolve o problema da rigidez (código difícil de mudar), da fragilidade (muda em um lugar, quebra em outro) e da imobilidade (impossível reaproveitar partes do código).

B.1) S — Single Responsibility Principle (Princípio da Responsabilidade Única)
"Uma classe deve ter apenas um motivo para mudar."
• Explicação detalhada: Uma classe não deve ser uma "ferramenta canivete suíço". Se uma classe Pedido calcula o total, salva o pedido no banco de dados e gera um PDF, ela tem três motivos diferentes para mudar (muda a regra de imposto, muda o banco, muda o layout do PDF).
• Solução: Separe em Pedido (dados), PedidoRepository (banco) e PedidoRelatorio (PDF).

B.2) O — Open/Closed Principle (Princípio Aberto/Fechado)
"Entidades de software devem estar abertas para extensão, mas fechadas para modificação."
• Explicação detalhada: Quando você precisa adicionar um novo comportamento ou recurso ao sistema, você deve apenas adicionar código novo (estender), e nunca alterar o código que já funciona (modificar). Isso evita gerar bugs em funcionalidades antigas.
• Solução: Em vez de usar vários blocos if/else ou switch para verificar tipos (ex: if (tipo == "Credito")), utilize interfaces ou classes abstratas. Se um novo tipo de pagamento surgir (ex: "Pix"), você apenas cria uma nova classe que implementa aquela interface, sem mexer no motor principal de pagamentos.

B.3) L — Liskov Substitution Principle (Princípio da Substituição de Liskov)
"Classes derivadas devem ser substituíveis por suas classes base sem quebrar o sistema."
• Explicação detalhada: Se a classe B herda da classe A, eu devo conseguir trocar A por B em qualquer parte do sistema sem que o comportamento quebre ou lance exceções inesperadas.
• O clássico erro: A classe Quadrado herda de Retangulo. Ao mudar a altura do Quadrado, a largura muda junto por regra geométrica, quebrando a expectativa de quem estava usando a lógica de um Retangulo (onde largura e altura mudam de forma independente). Herança não deve ser usada apenas para reaproveitar código, mas sim se a relação for estritamente verdadeira.

B.4) I — Interface Segregation Principle (Princípio da Segregação de Interfaces)
"Uma classe não deve ser forçada a depender de métodos que ela não utiliza."
• Explicação detalhada: É melhor criar várias interfaces específicas e pequenas do que uma única interface "gorda" e genérica.
• Exemplo prático: Se você criar uma interface Ave com os métodos bicar() e voar(), e depois criar a classe Pinguim implementando Ave, o pinguim será forçado a implementar voar(), jogando uma exceção ou ficando com um método vazio. A solução é segregar: criar a interface Ave e a interface AveQueVoa.

B.5) D — Dependency Inversion Principle (Princípio da Inversão de Dependência)
"Dependa de abstrações, não de implementações concretas."
• Explicação detalhada: Módulos de alto nível (a lógica de negócio principal) não devem depender de módulos de baixo nível (detalhes como o banco de dados específico, uma biblioteca de terceiros ou um SDK de envio de SMS). Ambos devem depender de abstrações (interfaces).
• Exemplo prático: Sua classe de negócio não deve instanciar diretamente um MySQLConnection. Ela deve depender de uma interface chamada DBConnection. Dessa forma, se amanhã você quiser trocar o banco para PostgreSQL ou MongoDB, sua lógica de negócio continuará intacta, mudando apenas a peça de baixo nível que se conecta a ela.

C) Resumo da Sinergia

Conceito: Clean Code;
Foco Principal:	Legibilidade, simplicidade e clareza do texto do código.;
Onde atua: Micro-nível (dentro de métodos, variáveis e funções).
		
Conceito: SOLID;
Foco Principal:Flexibilidade, desacoplamento e estabilidade da estrutura.;
Onde atua: Macro-nível (relação entre classes, objetos e módulos).
